# AV-TokenVault MVP Design

## Goal

Build a local-first prototype for audio/video tokenization and vector storage. The first version prioritizes a complete functional loop over polished UI or heavy model integration.

The MVP must support:

- Uploading local video or audio files.
- Extracting video frames and audio tracks from video files.
- Segmenting audio files or extracted audio tracks.
- Generating placeholder embeddings through pluggable encoder interfaces.
- Persisting metadata, extracted artifacts, job logs, and embeddings in SQLite.
- Displaying job status, extracted frames, audio segments, logs, and storage counts in a simple Next.js UI.

## Confirmed Stack

- Backend: Python, FastAPI, SQLAlchemy, SQLite.
- Frontend: Next.js, shadcn/ui.
- Local environment: macOS with conda.
- Python runtime: use a conda environment with Python 3.11.
- Media processing: FFmpeg, invoked from Python.
- First encoder implementation: deterministic mock encoders for image and audio embeddings.

## Non-Goals For MVP

- No login or permission system.
- No server deployment.
- No distributed queue, Celery, or worker cluster.
- No complex multimodal QA or model training.
- No Chroma or FAISS dependency in the first pass.
- No strict discrete-token model integration in the first pass.

## Architecture

The system has three main layers:

1. Frontend workbench
   - Provides upload, processing controls, task status, logs, frame previews, audio segment table, and summary counts.
   - Polls backend job APIs while processing is active.

2. FastAPI backend
   - Receives uploads and stores original media files.
   - Creates processing jobs.
   - Runs media extraction and encoding in a local background task.
   - Serves metadata and extracted artifact files to the frontend.

3. Local persistence
   - Stores uploaded files and extracted artifacts under `data/`.
   - Stores metadata, job state, logs, and embedding vectors in SQLite.
   - Provides a `VectorStore` interface so Chroma or FAISS can be introduced later without rewriting the pipeline.

## API Design

```text
GET  /health
POST /api/media/upload
POST /api/jobs/{job_id}/start
GET  /api/jobs
GET  /api/jobs/{job_id}
GET  /api/jobs/{job_id}/logs
GET  /api/media/{media_id}
GET  /api/media/{media_id}/frames
GET  /api/media/{media_id}/audio-segments
GET  /api/media/{media_id}/stats
GET  /api/files/{artifact_path}
```

`POST /api/media/upload` creates both a `media_assets` row and a pending `processing_jobs` row. `POST /api/jobs/{job_id}/start` starts local background processing.

`GET /api/files/{artifact_path}` only serves files under the project `data/` directory. The backend must normalize and validate the requested path before returning a file so clients cannot read arbitrary local files.

## Processing Flow

1. User uploads `.mp4`, `.mov`, `.wav`, or `.mp3`.
2. Backend stores the file under `data/uploads/`.
3. Backend detects whether the file is video or audio.
4. Backend creates a pending job.
5. User starts processing from the UI.
6. Backend executes a background task:
   - For video:
     - Probe media metadata.
     - Extract frames at a fixed interval.
     - Extract audio as WAV.
     - Split extracted audio into segments.
   - For audio:
     - Convert to WAV when needed.
     - Split audio into segments.
   - Generate image embeddings for extracted frames.
   - Generate audio embeddings for audio segments.
   - Persist all records and logs.
7. Frontend polls job state and displays results.

## Default Processing Parameters

- Processing mode: `full`.
- Frame interval: `2` seconds.
- Segment duration: `5` seconds.
- Maximum frames per video: `120`.
- Image encoder: `mock-image-encoder`.
- Audio encoder: `mock-audio-encoder`.

## UI Design

The first UI is a single local workbench page.

It includes:

- File upload control.
- Processing parameter controls.
- Start processing button.
- Job status and progress display.
- Storage statistics: frame count, audio segment count, embedding count.
- Video frame preview grid.
- Audio segment table.
- Job log panel.
- Basic task list for recently uploaded media.

The UI should be simple and clear. Visual polish is secondary to a complete demonstrable workflow.

## Error Handling

- If FFmpeg is missing, backend processing fails with a readable job error and log entry.
- Unsupported file extensions are rejected at upload time.
- Failed processing updates the job status to `failed` and stores `error_message`.
- Frontend displays backend error messages and job logs.

## Local Execution Constraints

- The MVP is designed for one local user on one machine.
- The backend may run jobs through FastAPI background tasks or a small in-process worker.
- It is acceptable for the first version to process one media job at a time.
- Long-running jobs should remain observable through persisted job status, progress, and logs.
- The frontend and backend should be configured for local development ports only.

## Verification

MVP verification should cover:

- Backend unit tests for database creation and mock encoders.
- Backend API smoke tests for health, upload, and job creation.
- Media pipeline smoke test once FFmpeg is available.
- Frontend lint/build once the UI is scaffolded.
- Manual demo with one short video and one short audio file.

## Future Extensions

- Replace or supplement SQLite embedding storage with Chroma or FAISS.
- Add real image encoders such as OpenCLIP or DINOv2.
- Add real audio encoders such as Whisper encoder, Wav2Vec2, HuBERT, or EnCodec.
- Add discrete-token support if the advisor requires strict token IDs.
- Add similarity search and text-to-media retrieval.
